# Vote-lock migration UI handoff

Status: interactive design draft on `codex/v6-votelock-unlock-relock-ui`. The UI is mounted in the real Governance, DTF Overview, and Portfolio page layouts. It does not read migration eligibility or send wallet transactions. Governance and vote-lock behavior require engineer review before live integration.

## Intended account journey

1. A connected holder with shares in an old RSR-backed, per-DTF vote-lock vault sees a migration warning after that vault is retired and its unstaking delay is zero. The warning replaces the Governance vote-lock action, sits at the top of the Overview right rail, and appears above Portfolio's chart and on the affected position row. Governance also shows a wallet-check prompt to disconnected visitors. Unaffected accounts retain the regular vote-lock action.
2. The centered modal shows the holder's full old-vault **share balance**, without an amount input. Redeeming those shares returns RSR to the wallet in the same transaction; there is no separate withdrawal transaction or waiting period.
3. Before the holder begins, the flow checks the shared vlRSR vault's RSR allowance and presents a two-step path when it is already sufficient, or a three-step path when approval is required. A redemption preview can estimate the RSR amount, but finite allowances must be checked again against the actual RSR received. If approval is required, the holder approves exactly that received amount. The received amount is shown in the approval and deposit steps.
4. The holder deposits the RSR into the shared vlRSR vault. The normal path takes two wallet transactions; a required approval makes it three. Completion hides the temporary warnings and returns the regular vote-lock action.
5. A rejected wallet request leaves the current action ready to retry. After redemption, the old position disappears from Portfolio and the received RSR appears as a wallet balance. Governance, Overview, and Portfolio retain a **Continue migration** callout, and reopening the modal starts at approval or locking rather than redemption. The preview restores that step after a reload in the same browser tab.

## Copy and state contract

- The disconnected Governance prompt deliberately calls attention to the upgrade, then says it only matters to holders of an old vote-lock that has not moved. It explains that those locks no longer vote or earn rewards, and that holders who already moved or only used vlRSR are done. In the real implementation, **Connect to check** must connect a wallet and resolve eligibility before showing an account-specific warning; the prototype merely switches to its affected fixture.
- Show **Action needed** only after a connected wallet is confirmed to hold an eligible old position. After a confirmed redemption, say the RSR is in the wallet and the migration still needs to be finished. An unaffected wallet should not inherit the affected warning from a previous account or DTF. Do not infer migration completion from zero old shares alone.
- Keep completed steps visible with the actual receipt hash and a link to that chain's explorer. Show a submitted transaction's hash while it is pending when available. If the final transaction confirms while the modal is closed, keep a visible completion acknowledgment instead of removing the callout silently.
- Approval is a conditional transaction, not a ceremonial step. The step count should reflect the live allowance, and any change after redemption must be explained before asking for an extra signature. The first step shows old-vault shares; the next step shows **actual RSR received**. If a redemption estimate is added, label it as an estimate until the receipt resolves.
- The success message must match the actual delegation result. The implementation artifact self-delegates in the deposit call, while earlier design discussion assumed existing delegates might carry over. Resolve that contract before claiming the holder is ready to vote or that delegates were preserved.

## What the draft simulates

- `?voteLockMigration=affected|disconnected|unaffected` selects account state in development builds. The affected LCAP demo carries its warning across Governance, Overview, and Portfolio after the parameter is dropped during same-tab navigation. On a fresh session, no parameter renders no migration UI. `?voteLockMigrationApproval=required` selects the three-step approval path; otherwise the preview shows two steps from the start. `?voteLockMigrationResult=rejected` rejects the first wallet request, then allows retry, including after a reload.
- The modal advances its status on timers. It never calls a wallet, signs, submits, checks allowance, or waits for a real receipt. The disconnected card's **Connect to check** button changes local display state; it does not connect a wallet.
- The modal uses sample balances of 1,210 old-vault shares and 1,250 RSR received. These are independent placeholders, not a share-to-RSR calculation. Portfolio's development-only fixture shows the old row before redemption, wallet RSR after redemption, and a new vlRSR position on completion. Engineering must replace these with live vault shares and the actual RSR returned by redemption.
- Confirmed step rows keep their shortened sample transaction references when the final step completes; the last row also shows the locked amount and Done action. The references link to the position chain's explorer. The hashes are synthetic, so those explorer pages will not show real migration transactions.
- Governance and Overview use the current DTF's token symbols when available and fall back to the LCAP sample symbols while data is loading. Preview progress is saved in development-only `sessionStorage` under `register.vote-lock-migration-preview.v2`, keyed by chain, old vault, and the fixed demo account. It preserves the approval decision, one-time rejection, and a submitted transaction's simulated confirmation deadline across reload and same-tab navigation. This is not evidence of an on-chain transaction. Clear that key and `register.vote-lock-migration-preview-mode.v1` to restart the demo. Separate tabs have separate preview progress.

## Engineering work before release

- Read the connected account's old-vault shares and the vault's retired/zero-delay status from live sources. Only offer this route for RSR-backed old vaults; old vaults backed by other tokens cannot deposit into shared vlRSR. Establish the correct old and new vault identities by chain and account. Replace URL-selected state and the Portfolio fixture with live wallet and SDK reads.
- Wire the old-vault redemption, conditional exact RSR approval, and shared-vault deposit through the SDK and wallet transaction state. Read the live RSR allowance before showing the step count; use the redemption preview for an estimate, then recheck allowance against the confirmed RSR received. A finite allowance may change the expected path. Use `Amount`/`bigint` for on-chain quantities. Derive the received RSR from the confirmed redemption rather than assuming a fixed share-to-asset rate.
- Resolve delegation before release. The implementation artifact's deposit self-delegates in the same call; the earlier design assumption was to preserve existing delegates. The UI currently avoids promising either outcome.
- Replace timer transitions and preview storage with wallet and receipt states, scoped to the real connected account and old vault. Derive the recovery stage from confirmed redemption, allowance, wallet RSR, and shared-vault balance; never treat zero old-vault shares alone as completion or ask a holder to redeem twice. If a transaction is pending across navigation or reload, recover its receipt before offering the next action. Confirm completion from the deposit receipt and live vault balance, then hide warnings.
- Replace synthetic hashes with confirmed receipts and link every transaction reference through `getExplorerLink` for the position chain. Include approval only when an approval transaction was actually sent. Review copy, localization, analytics, and transaction errors. Governance and vote-lock behavior require engineer review under the repository rules.
