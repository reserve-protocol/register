## Task and information hierarchy

Usage sketch, subject to the verified conditions in Claude's report:

1. A disconnected visitor identifies the current rebalance, what is happening,
   what blocks action, who can act and which deadline changes eligibility. Wallet
   uncertainty is not automatically “unauthorized,” and a permissionless countdown
   must not imply community launch exists where it does not.
2. An authorized launcher inspects requirements and relevant asset/risk details,
   completes any preparation, launches, and sees confirmation and current activity
   without losing the rebalance identity or remaining work.
3. A returning participant sees an auction end and the next required work. Prior
   progress remains understandable; the number of runs does not predict a final
   total, and stale display data does not authorize a second launch.

At a glance: identity, meaningful state, blockers/required preparation, access,
next applicable action and the relevant timer. Supporting: verified progress,
buy/sell summary, live activity and the explanation needed to decide. Secondary:
expanded asset/bid detail, supporting diagnostics and provenance as evidenced.
These are information priorities, not an already-approved panel arrangement.

Restrictions, required actions and material warnings must remain visible outside
hover/disclosure. No dependence on section headings to carry actionability.
Status, timer and button should not repeat the same full sentence three times.
All final visible wording must come from production or explicit user approval.

## State continuity

This checklist names presentation invariants, not verified protocol transitions.
Claude's audit supplies exact reachability and execution conditions.

| Transition                                          | Preserve                                                                 | Legitimate change / risk to prove                                                                                                       |
| --------------------------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Disconnected → connected / account or chain changes | Rebalance and inspected context; unrelated disclosure state              | Re-evaluate access without retaining the old account's permission or enabling stale work.                                               |
| Preparation editing → saved → returned              | Draft, validation and saved state according to product semantics         | Saved is not transaction-final unless the source establishes that; errors do not silently reset edits.                                  |
| Ready → wallet request → submitted                  | Intended action, relevant parameters, rebalance identity                 | Distinct wallet instruction and submitted status; repeat activation blocked.                                                            |
| Submitted → confirmed → refreshed activity          | Operation identity and confirmation evidence                             | Receipt and refreshed auction data are distinct; no stale Ready flash or fabricated immediate rebalance completion.                     |
| Reject/error → retry                                | Verified retry scope and inputs/progress that survive                    | Show visible actionable recovery; do not replay already successful work.                                                                |
| Live auction → ended → more work                    | Rebalance identity, run history and inspected evidence where valid       | Current-auction timer ends, next work is derived; do not increment count optimistically without source confirmation.                    |
| Loading/unavailable → recovered                     | Known identity and valid completed work                                  | Missing does not become zero; stale is displayed only if the source supports that category.                                             |
| Current → historical                                | Same rebalance identity and truthful confirmed outcomes                  | Transfer ownership without duplicates; focus remains purposeful if an active control disappears.                                        |
| Narrow/wide / secondary detail open/closed          | Draft, active operation, chart selection and open-state where applicable | Rearrangement must not remount execution, discard inputs or create two live trees.                                                      |
| Two current records                                 | Per-rebalance disclosure, drafts and operation identity                  | Actions and responses cannot cross into the other record. This is a pressure fixture, not a claim that production frequently shows two. |

## Transaction truth and sources

Before fixture implementation, classify every number as input, requirement,
estimate, current observation, submitted record, confirmed result or unavailable.
Classify chart values separately from actual bid amounts. Keep transaction hash,
auction identity and rebalance identity separate. Neither disabled styling nor a
successful lab transition proves an on-chain prerequisite.

Use source-derived fixtures and clearly labeled synthetic overlays. No silent
use of financial estimates as confirmed outcomes. An `isLoading` or fixture
selector must not collapse wallet resolution, request error and empty results.
No live wallet/SDK write imports in the eventual lab simulator; production
adapters, permissions, price/weight math and refresh reconciliation stay
engineer-owned. This package does not specify a new wire contract.

## First review slice and migration preservation

After audit intake: one complete authorized-launcher preparation state plus an
ongoing auction with prior runs. Include enough real asset/bid content to expose
density. Exercise preparation → launch waiting → monitoring where verified.
Then pressure the same composition with missing data and hybrid preparation,
before extending the remaining matrix. No requirement for an interim user review
of empty scaffolding or basic primitives.

Preserve the refined history table: card color, no gray row dividers, static
rows, independent proposer links, compact date format, numeric whole-cell
centering and its new width allocation. Do not make historical rows clickable
again to compensate for missing functionality in the current workspace.

  none of the above design evidence authorizes live implementation.
